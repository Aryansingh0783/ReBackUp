/01   The problem

It's never the Documents folder.

You back up Documents, wipe the disk, and three days later find the things you actually lost. None of it lives where you looked — it's scattered across %APPDATA%, %LOCALAPPDATA%, Program Files and the Windows Credential vault, and most of it is encrypted to an account that no longer exists.

01

Saved passwords

Encrypted with DPAPI, bound to the Windows account you're about to delete. Copying the profile folder does not bring them back.

02

Work that was never pushed

A repo with uncommitted changes, or no remote at all. It exists on exactly one disk, and you're about to format it.

03

The thousand small things

An SSH key. A .env. The API token in .npmrc. Editor settings you spent a year tuning.

/03   How it works

Five stages, one honest failure mode

01

Scan — the MFT fast path

walkdir costs one directory-open plus a stat per file and is dominated by kernel round-trips. The NTFS Master File Table already holds every name, parent pointer, size and timestamp on the volume — so ReBackUp opens \\.\C: and parses it directly. One long sequential read instead of millions of syscalls. Needs admin; falls back to a parallel walk automatically and tells you it did.

02

Choose — profiles, not checkboxes

A profile is a bundle of glob patterns plus optional secret actions. %ENV% expands at plan time, not definition time, so a profile file is portable between machines. Your edits merge over the built-ins by id, so upgrading keeps them.

03

Seal — Argon2id + AES-256-GCM

Decrypted passwords exist only inside Zeroizing containers, are assembled into a CSV in memory, sealed, and dropped. Nothing secret is ever written to disk in the clear. KDF parameters are authenticated as associated data, so nobody can downgrade mCostKib to 8 KiB and still decrypt.

04

Verify — the step that earns trust

Every file is hashed during the copy, then re-hashed from disk and compared. If anything mismatches, the report says do not reset yet. This is the check that catches a dying USB stick before it costs you the data.

05

Restore — idempotent by design

restore.ps1 reads manifest.json at run time instead of baking paths in, verifies each hash before writing, and skips files that already match. Re-running after a partial restore is safe and nearly free. It rewrites \Users\<old>\ to your new username automatically.

# after the clean install
.\restore.ps1 -DryRun          # preview, change nothing
.\restore.cmd                  # do it (safe to re-run)

rebackup unseal --in secrets\opera-gx-default-passwords.csv.rbu --out pw.csv
# import in the browser, then destroy the plaintext
rebackup shred --path pw.csv

/05   Security model

Both halves, stated plainly

A backup tool that oversells its guarantees is worse than one that undersells them. Here is what holds, and what doesn't.

What is protected

Secrets live only in Zeroizing memory, wiped on drop. Sealing happens in memory — only the sealed blob touches disk. Argon2id at 64 MiB, AES-256-GCM, KDF parameters authenticated so they can't be downgraded. Types holding secrets have no Serialize impl — they physically cannot reach the UI or the manifest. A manifest audit aborts the run if an unsealed file lands under secrets/. Wrong passphrase and tampered ciphertext give the same error, deliberately.

What is not

The staging folder is plaintext for everything that isn't a secret — your documents are documents. Shredding is best-effort on an SSD; wear levelling may have already moved the blocks. Lose the passphrase, lose the sealed data — no recovery, no escrow. DPAPI is scoped to your logon session, so another account's profile and an offline disk are both out of reach. Chrome 127+ app-bound encryption is not defeated; it's detected, and you're routed to the browser's own export. ssfn* sentry files are bound to your Windows SID, which changes on reinstall.
